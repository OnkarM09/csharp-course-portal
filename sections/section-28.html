Section 28: Exception Handling & Defensive Programming

Detailed architectural breakdown integrating comprehensive explanations, syntax reference matrices, compiler internals, and production C# code.

1. What Are Exceptions & Call Stack Unwinding

An exception is an abnormal event or error condition occurring during application runtime that interrupts the standard execution flow. When an error is encountered, the runtime instantiates an Exception object and initiates Call Stack Unwinding: the CLR walks up the stack frame by frame looking for an enclosing catch block capable of handling that exception type.

2. try-catch-finally Execution Mechanics

  1. try Block: Encloses risky code that might throw an exception.
  2. catch Block: Handles the specific exception type. Multiple catch blocks must be ordered from most specific to least specific.
  3. finally Block: GUARANTEED TO ALWAYS EXECUTE, regardless of whether an exception occurred, was caught, or whether the method exited early via return!
try-catch-finally Execution Flow 
try
{
    Console.WriteLine("1. Entering try block");
    int zero = 0;
    int result = 100 / zero; // Throws DivideByZeroException
    Console.WriteLine("This line will NEVER execute.");
}
catch (DivideByZeroException ex)
{
    Console.WriteLine($"2. Caught specific exception: {ex.Message}");
}
finally
{
    Console.WriteLine("3. Finally block executes unconditionally!");
}

4. Modern Exception Filters (when Keyword)

Exception filters allow a catch block to execute only when an arbitrary boolean condition evaluates to true. Unlike checking inside the catch body, exception filters inspect the condition without unwinding the stack, preserving pristine stack traces for crash dump diagnostics:

Exception Filters with when 
try
{
    await httpClient.GetAsync("https://api.internal/data");
}
catch (HttpRequestException ex) when (ex.StatusCode == System.Net.HttpStatusCode.NotFound)
{
    Console.WriteLine("Endpoint was not found (404). Falling back to cache.");
}
catch (HttpRequestException ex) when (ex.StatusCode == System.Net.HttpStatusCode.Unauthorized)
{
    Console.WriteLine("Authentication failed (401). Refreshing security token.");
}

5. Re-throwing: throw vs throw ex (Stack Trace Preservation)

📊 Diagram: throw vs throw ex Stack Trace Preservation
PROPER RE-THROW: throw;
[Original Error: Line 142 in Repository.cs] ---> [Line 85 in Service.cs] ---> [Line 20 in Controller.cs]
(100% of stack trace forensic history is completely preserved!)

DESTRUCTIVE RE-THROW: throw ex;
[Line 85 in Service.cs] ---> [Line 20 in Controller.cs]
(Original crash location at Line 142 in Repository is PERMANENTLY WIPED OUT!)
Correct Rethrow Pattern 
try
{
    ProcessPayment();
}
catch (Exception ex)
{
    // Log the error
    Logger.LogError(ex);

    // CORRECT: Preserves entire stack trace
    throw; 

    // WRONG / DESTRUCTIVE: Resets stack trace to this exact line!
    // throw ex; 
}

6. Fatal Exception Anti-Patterns

🟠 Compiler Trap & Common Gotcha

The Ultimate Anti-Pattern (Pokemon Exception Handling): 

try { DoRiskyOperation(); } catch (Exception) { /* do nothing */ }

Consequence: Swallows critical out-of-memory errors, security failures, and bugs silently. The program continues in a corrupted state, causing data corruption hours later. Always catch specific exceptions, and at minimum log the failure!
