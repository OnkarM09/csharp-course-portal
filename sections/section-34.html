Section 34: C# 11 New Features (.NET 7)

Detailed architectural breakdown integrating comprehensive explanations, syntax reference matrices, compiler internals, and production C# code.

1. Overview of C# 11

C# 11, released as part of .NET 7, brings a host of new features designed to improve developer productivity, enhance code clarity, and enable new programming patterns. While some features are minor quality-of-life improvements, others introduce significant capabilities, particularly around string manipulation, pattern matching, and type definitions. The primary goals behind the C# 11 features include:

  • Simplifying Code: Making common tasks easier to write and read, reducing boilerplate.
  • Enhancing Pattern Matching: Expanding the power and expressiveness of pattern matching for more robust data analysis.
  • Improving Performance: Introducing features that can lead to more efficient code, especially around memory management and struct usage.
  • Enabling Future Features: Laying groundwork for potential future C# and .NET capabilities. Many of these features build upon existing C# constructs, extending their utility rather than introducing entirely new concepts from scratch. This allows developers to gradually adopt them and integrate them into their existing codebase. Here's a brief look at some of the key areas C# 11 focuses on:
  • Raw String Literals: A highly anticipated feature that simplifies working with strings containing multiple lines, special characters, or embedded code (like JSON, XML, or SQL queries).
  • List Patterns: Extends C#'s powerful pattern matching to work with sequences (arrays, lists), allowing for more declarative and readable checks against data structures.
  • File-Local Types: A new access modifier that helps reduce naming conflicts and improve code organization within a single source file.
  • Required Members: A mechanism to enforce that certain properties or fields of a class or struct must be initialized during object creation, improving type safety and reducing potential null reference exceptions.
  • Auto-Default Structs: Simplifies the initialization of struct fields by automatically zero-initializing them if not explicitly set.
  • Ref Fields: Allows fields within ref struct types to be references (ref) to other locations in memory, enabling more control over memory layouts and potentially higher performance in advanced scenarios. These features collectively aim to make C# an even more expressive, productive, and robust language for building a wide range of applications, from high- performance systems to everyday business logic.

2. Raw String Literals

Raw string literals are a new string literal format introduced in C# 11 that significantly simplifies working with strings containing special characters, multiple lines, or embedded code (like JSON, XML, or regular expressions). They eliminate the need for cumbersome escape sequences, making the string content much more readable and closer to its intended literal form. Problem Solved:

Before C# 11

, if you wanted to include special characters like backslashes (\), quotes ("), or newlines (\n) directly in a string, you had to use escape sequences. For multi-line strings, you often had to concatenate multiple lines or use @ verbatim string literals, which still required escaping double quotes.

Example

of old way: string json1 = "{\n \"name\": \"Alice\",\n \"age\": 30\n}"; // Requires escaping newlines and quotes

C# 
string json2 = @"{
    ""name"": ""Bob"",""age"": 25
}"; // Requires doubling internal quotes

This becomes very unreadable with complex JSON, XML, SQL queries, or regular expressions.

Syntax

of Raw String Literals: Raw string literals start and end with at least three double-quote characters (""").

  • No Escaping: Inside the delimiters, all characters (including newlines and double quotes) are interpreted literally. You don't need \ or "" for escaping.
  • Indentation: The content's indentation relative to the closing delimiter is removed. This allows you to indent your raw string literal cleanly within your code without that indentation being part of the string itself.
  • Delimiter Length: If your string content contains """, you can use more than three double quotes as delimiters (e.g., """" or """""). The closing delimiter must match the opening delimiter's length.
  • Interpolation: Raw string literals fully support string interpolation. If your string contains curly braces ({ or }), and you intend them to be literal, you can use more $ signs than the number of curly braces used for interpolation. For example, if you use two $ ($$), then {...} will be literal and {{...}} will be interpolated. Basic Example:
C# 
// Simple multi-line string

This is the first line. This is the second line. And a third line. """;

C# 
Console.WriteLine(multiLineString);
// Output will be:
// This is the first line.
// This is the second line.
// And a third line.

Notice how the leading whitespace before "This is" is automatically removed because it aligns with the closing """.

3. List Pattern

C# 11 introduces List Patterns, which extend the capabilities of pattern matching to allow you to match against elements in a list, array, or any type that implements IEnumerable. This feature provides a concise and expressive way to inspect the structure and contents of sequences, making code that deals with collections more readable and less error-prone. Problem Solved:

Before C# 11

, checking the structure of a list often involved multiple conditional statements (if checks) for Count and individual element access (e.g., list[0], list[1]), followed by more checks on the elements themselves. This could quickly become verbose and difficult to read for complex scenarios.

Syntax: and Features:

List patterns use square brackets [] to enclose the patterns for the elements you want to match.

  • Matching Specific Elements: You can specify literal values or declaration patterns for elements at specific positions.
C# 
int[] numbers = { 1, 2, 3 };
C# 
{
    Console.WriteLine("Matches [1, 2, 3]");
}
  • Discard Pattern (_): Use _ to match any single element at a specific position without binding it to a variable.
C# 
int[] numbers = { 10, 20, 30 };

if (numbers is [10, _, 30]) // Matches if first is 10, second is anything, third is 30

C# 
{
    Console.WriteLine("Matches [10, _, 30]");
}
  • Range Pattern (.. - slice pattern): This powerful feature, often used within list patterns, allows you to match zero or more elements. It's known as a "slice pattern." (We'll cover Slice Pattern in detail next, but it's essential for List Patterns).
C# 
int[] data = { 1, 2, 3, 4, 5 };

if (data is [1, .., 5]) // Matches if it starts with 1, ends with 5, and has any number of elements in between

C# 
{
    Console.WriteLine("Matches [1, .., 5]");
}
  • You can use only one .. in a list pattern.
  • The .. pattern can optionally be followed by a variable to capture the matched sub-sequence (e.g., [1, ..var middle, 5]).
  • Nested Patterns: List patterns can be nested within other patterns (e.g., property patterns, var patterns).
C# 
record Point(int X, int Y);
record Shape(string Type, Point[] Vertices);
Shape square = new("Square", new Point[] { new(0,0), new(1,0),new(1,1), new(0,1) });
C# 
{
    Console.WriteLine("It's a square and has a vertex at (1,1)");
}
  • Length Check: The pattern inherently checks the length of the sequence based on the number of elements specified in the pattern (unless .. is used).
C# 
int[] numbers = { 1, 2 };

if (numbers is [1, 2, 3]) // False, length mismatch

C# 
{
    // This won't execute
}

4. Slice Pattern

The Slice Pattern (..) is a powerful component primarily used within List Patterns (as discussed in the previous section). It allows you to match zero or more elements at a specific position within a sequence (like an array, list, or ReadOnlySpan<T>), effectively "slicing" out a portion of the input. Purpose:

  • To capture a sub-sequence of elements from the input collection.
  • To ignore an arbitrary number of elements within a pattern match.

Syntax: and Behavior:

The slice pattern is denoted by two dots: ..

  • Matching Zero or More Elements:
  • When .. appears by itself (e.g., [1, .., 5]), it matches any number of elements (zero or more) at that position. It's a way to say "anything here, and any amount of it."
  • Capturing a Sub-sequence (.. varName):
  • You can combine .. with a var pattern (e.g., [1, .. var middle, 5]). In this case, middle will capture a T[] (for arrays) or List<T> (for lists) containing the elements matched by the slice pattern. If the slice matches no elements, middle will be an empty array or list.
  • The type of varName will be inferred based on the context of the collection type.
  • Placement: A list pattern can contain at most one slice pattern (..). You cannot have [.., _, ..] because it would be ambiguous.
  • Supported Types: Slice patterns work with types that can be "sliced" in a meaningful way, primarily Array, List<T>, Span<T>, ReadOnlySpan<T>, and types that are "sliceable" by convention for pattern matching. Illustrative Examples:

5. Var Pattern

The var pattern is a relatively small but useful enhancement in C# 11 that allows you to use the var keyword in a pattern matching context where it was previously not permitted, specifically within a property pattern. Problem Solved / Enhancement: Prior to C# 11, if you wanted to deconstruct an object using a property pattern and assign a property's value to a new variable, you had to explicitly state the type of the property, even if that type was obvious or you didn't strictly need to specify it.

Example

of old way (pre C# 11):

C# 
record Product(string Name, decimal Price);
Product p = new("Laptop", 1200.50m);
// Old way: Must specify 'string name' and 'decimal price'
C# 
{
    Console.WriteLine($"Product: {name}, Price: {price}");
}

This was verbose, especially if the property types were long or generic.

Syntax: and Behavior:

In C# 11, you can now use var within property patterns. The var pattern infers the type of the matched expression (the property's type) and assigns its value to a new variable.

C# 
record Product(string Name, decimal Price);
Product p = new("Laptop", 1200.50m);
// C# 11 new way: Using 'var' in property patterns
C# 
{
    Console.WriteLine($"Product: {name}, Price: {price}");
}
// More concise with positionals for records:
C# 
{
    Console.WriteLine($"Product (positional): {n}, Price: {pr}");
}

What the var pattern really does (in broader pattern matching context): The var pattern, when used in general pattern matching (not just property patterns), is an unconditional pattern. It always succeeds and captures the value of the matched expression into a new local variable.

Its type is implicitly the type of the expression being matched. It's equivalent to a declaration pattern (Type variableName) where Type is var.

6. File Local Types

C# 11 introduces a new access modifier, file, which allows you to declare types that are only visible and usable within the same source file (.cs file) in which they are declared. This feature is particularly useful for internal helper types that are specific to the implementation details of a single file, preventing naming conflicts and improving code encapsulation. Problem Solved:

Before C# 11

, if you had a helper class, struct, or interface that was only meant to be used by other types within the same .cs file, your options were limited:

  1. private nested type: This tightly couples the helper type to a specific outer class, making it inaccessible to other top-level types in the same file.
  2. internal type: This makes the type visible across the entire assembly. This could lead to:
  • Naming Conflicts: If multiple developers in a large project create internal helper types with common names (e.g., Helper, Processor, State), it could lead to ambiguity or require cumbersome prefixing.
  • Unintended Usage: The internal type might accidentally be used by code outside its intended scope (but still within the same assembly).
  • Polluting IntelliSense: The helper type might appear in IntelliSense for unrelated parts of the assembly. File-local types provide a perfect solution for these scenarios, offering a scope narrower than internal but broader than private nested types.

Syntax

You declare a file-local type by adding the file access modifier before the type declaration. file class MyFileLocalClass { /* ... */ } file struct MyFileLocalStruct { /* ... */ } file interface IMyFileLocalInterface { /* ... */ } file enum MyFileLocalEnum { /* ... */ } file record MyFileLocalRecord { /* ... */ }

Key Characteristics

  • Scope: A file type is accessible only within the .cs file where it is declared.
  • Default Visibility: If no explicit access modifier is given alongside file (e.g., just file class MyType), it behaves like file internal. You cannot specify public, protected, or private with file.
  • Nesting: File-local types can be top-level types or nested within other types. If a file-local type is nested within another type, its visibility is still constrained by the file modifier to the containing file.
  • Naming Conflicts: You can have multiple types with the same name across different files, as long as they are declared as file types. This eliminates naming conflicts for local helper types.
  • IntelliSense: file types will not appear in IntelliSense outside their declaring file.

7. Required Members

C# 11 introduces the required modifier for members (properties and fields) within classes and structs. This feature enables you to enforce that certain members of a type must be initialized by constructors or object initializers when an instance of the type is created. This improves type safety, reduces the likelihood of uninitialized data, and makes the intent of the API clearer to users. Problem Solved:

Before required members, there was no straightforward way to guarantee that specific properties of an object were always set during its construction, especially when using object initializers. Developers often relied on:

  • Constructor Overloads: Providing constructors with many parameters, which can become unwieldy for types with many properties.
  • Documentation: Relying on comments or external documentation to tell users which properties needed to be set.
  • Runtime Checks: Adding validation logic within constructors or property setters, which would only catch issues at runtime.
  • Nullable Reference Types: While useful, null cannot differentiate between an intentionally null value and a property that was simply forgotten to be initialized. required members provide a compile-time guarantee, preventing object creation if the required members are not initialized.

Syntax

You mark a property or field with the required keyword:

C# 
public class MyClass
{
    public required string Name { get; set; }
    public required int Id { get; init; } // Can be combined with 'init'
    public required string Description; // Can be a field
}

Key Characteristics and Rules

  • Initialization Requirement: Any required member must be initialized as part of the object's creation. This can happen in one of two ways:
  1. Directly in a constructor: The constructor explicitly assigns a value to the required member.
  2. Via an object initializer: When using new MyClass { Name = "...", Id = ... }, all required members must be present in the initializer list.
  • Compile-Time Enforcement: The compiler enforces this rule. If a required member is not initialized in either of these ways, a compile-time error occurs (CS9035).
  • init and set Accessors: required can be used with both set (mutable) and init (init-only) accessors.
  • Fields vs. Properties: Both required fields and required properties are supported.
  • No readonly with required fields (with some exceptions): A required field cannot also be readonly if it's meant to be initialized via an object initializer. This is because readonly fields can only be assigned in the constructor or during declaration. However, required properties can use init, which provides similar immutability after construction.
  • Inheritance:
  1. required members are inherited. If a base class has a required member, derived classes also inherit this requirement.
  2. Derived classes do not need to re-declare a base required member as required (though they can if they shadow it). The requirement from the base class applies to derived instances.
  • record types: required members work seamlessly with record types, including positional records (though for positional records, constructor parameters usually handle initialization).
  • Default Constructors: If a type has a required member but no explicit constructor, the compiler will generate a default parameterless constructor. However, this default constructor will not initialize the required member, meaning you must use an object initializer when creating an instance.

8. Auto Default Structs

C# 11 introduces a significant improvement for structs by ensuring that all fields of a struct are automatically initialized to their default values if they are not explicitly set by a constructor or an object initializer. This feature is known as Auto Default Structs. Problem Solved:

Before C# 11

, structs had strict rules regarding constructors and field initialization:

  • No Parameterless Constructors: Structs could not declare an explicit parameterless constructor. The runtime provided an implicit one that would zero-initialize all fields.
  • Definite Assignment Rule: If you declared a custom constructor in a struct, you had to explicitly assign a value to every field in that constructor. Failure to do so would result in a compile-time error (CS0171: Field 'field' must be fully assigned before control leaves the constructor). These rules often led to more verbose constructors, especially for structs with many fields, and could make it tricky to define constructors that only initialized a subset of fields. C# 11 Changes: In C# 11, the definite assignment rule for structs has been relaxed.
  • Explicit Parameterless Constructors: Structs can now declare an explicit parameterless constructor.
  • Automatic Zero-Initialization: If a constructor (explicit or implicit) does not explicitly initialize all fields, any uninitialized fields are automatically set to their default value (e.g., 0 for numeric types, false for bool, null for reference types, default for other value types).

Syntax: and Behavior:

There's no new keyword; it's a change in how the compiler handles struct initialization.

9. Ref Fields

C# 11 introduces ref fields (also known as ref fields in ref struct types), allowing fields within ref struct types to be references (ref) to other memory locations. This is a highly advanced feature primarily aimed at scenarios requiring very high performance and low-level memory control, often used in conjunction with Span<T> and related types. Background: What are ref structs?

Before understanding ref fields, it's crucial to recall ref structs (introduced in C# 7.2):

  • Memory Safety: ref struct types are stack-only types. This means they can only be allocated on the stack and cannot be boxed to the heap, used as type arguments for generics (unless the type argument is also a ref struct), or used in async methods. This restriction prevents them from outliving the stack frame they are declared in, which is crucial for memory safety when dealing with references to stack-allocated memory (like Span<T>).
  • Performance: They are designed for high-performance scenarios where allocating on the heap and garbage collection overhead need to be avoided. Span<T> is the prime example of a ref struct. Problem Solved / Enhancement: Prior to C# 11, ref structs could contain regular fields (value types or reference types), but they could not directly contain ref fields. This limited their ability to directly "point" to or hold references to specific memory locations within the ref struct itself, forcing workarounds or more complex patterns. ref fields allow a ref struct to:
  • Directly embed references to other stack-allocated data.
  • More effectively represent views into unmanaged or stack-allocated memory without copying.

Syntax

You declare a ref field by using the ref keyword before the field's type:

C# 
public ref struct MyRefStruct
{
    public ref int ValueRef; // A ref field pointing to an int
    public ref readonly string MessageRef; // A ref readonly field
}

Key Characteristics and Rules

of ref Fields:

  1. Must be in a ref struct: ref fields are only allowed within ref struct types. They cannot be used in regular structs or classes.
  2. ref readonly: You can declare a ref readonly field, meaning the reference itself can be reassigned (if not also readonly), but the data it points to cannot be modified through this field.
  3. Definite Assignment: Like all fields, ref fields must be definitely assigned in a constructor.
  4. ref local variables: ref fields are similar in concept to ref local variables (ref int x = ref y;).
  5. Lifetime Safety: The compiler strictly enforces ref safety rules (similar to Span<T>) to ensure that a ref field does not outlive the memory it refers to. This prevents dangling pointers.
  • The lifetime of the ref field must be equal to or shorter than the lifetime of the ref struct it is a part of.
  • The lifetime of the data that the ref field points to must be equal to or longer than the lifetime of the ref field itself.
  1. No static or readonly ref fields (initially): A ref field cannot be static. A ref field can be readonly if it is always initialized to a valid reference in the constructor and never changed afterward.
  2. No Default Constructor for ref struct with ref fields (usually): If a ref struct contains ref fields, it generally cannot have a parameterless constructor (implicit or explicit) because ref fields must be initialized to a valid reference at construction, which default or an empty constructor cannot guarantee.
  3. Pointers vs. References: ref fields are managed references, not unmanaged pointers. They benefit from garbage collection safety, but within the strict ref struct context.

Real-World Example (Simplified): Custom Span-like Type

This example demonstrates how ref fields could be used to build a custom Span-like structure. This is simplified and primarily for conceptual understanding, as Span<T> itself is highly optimized.

Why ref fields are advanced:

  • Memory Safety Concerns: The compiler's ref safety analysis is complex. Misusing ref fields can lead to memory corruption or crashes if the lifetime rules are violated.
  • Low-Level: They are typically used in scenarios where you are trying to avoid memory allocations and garbage collector pressure at all costs, often involving interoperability (P/Invoke) or very performance-critical libraries.
  • Rarely for Application Developers: Most application developers will not need to directly use ref fields. Instead, they will consume APIs that use them internally (like Span<T>). Benefits (for advanced scenarios):
  • Zero Allocation ref structs: Enables the creation of ref struct types that act as true views into memory, avoiding copies and heap allocations.
  • Extreme Performance: Critical for performance-sensitive code where every allocation or copy counts.
  • Expressiveness: Allows for clearer representation of memory layouts and direct manipulation of referenced data within stack-only types. ref fields are a niche but powerful addition to C# for highly optimized, low-level programming.

10. Points to Remember

C# 11 introduces a mix of quality-of-life improvements and powerful, low-level features. Here's a summary of the key takeaways for each feature:

  1. Raw String Literals:
Best Practice & Architecture Tip
  • Purpose: Simplify multiline strings, strings with special characters (quotes, backslashes), and embedded code (JSON, XML, SQL).
  • Syntax: Started and ended with at least three double-quotes (""").
  • Key Benefit: No escaping needed. Indentation relative to the closing delimiter is automatically removed. Supports enhanced interpolation with more $ signs.
  • Remember: Makes code much more readable and reduces errors when dealing with complex string content.
  1. List Pattern:
Best Practice & Architecture Tip
  • Purpose: Allows pattern matching against elements in sequences (arrays, lists, IEnumerable).
  • Syntax: Uses square brackets [] to define patterns for elements.
  • Key Components: Can match specific values, use _ (discard) for any single element, and .. (slice) for zero or more elements.
  • Remember: Great for deconstructing and checking the structure of collections in a concise and declarative way.
  1. Slice Pattern (..):
Best Practice & Architecture Tip
  • Purpose: Used within List Patterns to match zero or more elements in a sequence.
  • Syntax: Two dots ...
  • Key Behavior: Can be used to ignore elements ([1, .., 5]) or capture a sub-sequence ([1, .. var middle, 5]).
  • Remember: Only one .. allowed per list pattern. Essential for flexible sequence matching.
  1. Var Pattern (in Property Patterns):
Best Practice & Architecture Tip
  • Purpose: Allows using var within property patterns to infer the property's type and assign its value to a new variable.
  • Syntax: MyObject is { PropertyName: var variableName }.
  • Key Benefit: Reduces boilerplate and improves readability in property pattern matching by removing the need for explicit type declarations.
  • Remember: A small but helpful syntactic sugar for more concise pattern matching.
  1. File Local Types:
Best Practice & Architecture Tip
  • Purpose: Declare types (classes, structs, interfaces, enums, records) that are only visible within the single .cs file where they are defined.
  • Syntax: Use the file access modifier (e.g., file class MyHelper).
  • Key Benefit: Prevents naming conflicts in large projects, improves encapsulation, and cleans up IntelliSense by hiding internal helper types.
  • Remember: Provides a scope narrower than internal but broader than private nested types.
  1. Required Members:
Best Practice & Architecture Tip
  • Purpose: Enforce that specific properties or fields of a class or struct must be initialized during object creation.
  • Syntax: Use the required keyword (e.g., public required string Name { get; set; }).
  • Key Benefit: Compile-time safety that prevents uninitialized data, makes API contracts clearer, and reduces runtime errors.
  • Remember: Initialization must happen via a constructor or an object initializer. Inherited requirements are also enforced.
  1. Auto Default Structs:
Best Practice & Architecture Tip
  • Purpose: Relax definite assignment rules for structs, allowing uninitialized fields in constructors to be automatically set to their default values (zero-initialized).
  • Key Benefit: Reduces boilerplate in struct constructors, makes structs more flexible, and allows explicit parameterless constructors.
  • Remember: Simplifies struct definitions and aligns default initialization behavior more closely with classes.
  1. Ref Fields:
Best Practice & Architecture Tip
  • Purpose: Allows fields within ref struct types to be references (ref) to other memory locations.
  • Syntax: public ref int MyRefField;.
  • Key Context: Only applicable within ref structs (stack-only types).
  • Key Benefit (Advanced): Enables creation of highly optimized, zero- allocation data structures that provide views into existing memory without copying.
  • Remember: A very advanced, low-level feature primarily for performance-critical scenarios. Requires strict adherence to ref safety rules to prevent memory issues. Most application developers will consume APIs that use these internally, rather than directly implementing them. C# 11 reinforces the language's strengths in both high-level productivity and low-level performance, offering tools for a wide range of programming challenges.
