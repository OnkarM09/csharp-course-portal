Section 19: Garbage Collection, Destructors & IDisposable

Detailed architectural breakdown integrating comprehensive explanations, syntax reference matrices, compiler internals, and production C# code.

1. Managed vs Unmanaged Memory & GC Roots

In C#, memory allocation is managed by the Garbage Collector (GC). When memory pressure triggers a collection, the GC builds a graph of all live objects reachable from GC Roots (active stack references, static fields, and CPU registers). Any object on the heap not connected to a live root is marked as garbage and swept away.

2. GC Generations: Gen 0, Gen 1, Gen 2 & LOH

The CLR GC is generational, based on the empirical rule that newly allocated objects tend to have short lifespans:

GenerationClassificationObject Types StoredCollection Frequency & Cost
Gen 0EphemeralShort-lived locals, temporary strings, loop buffersExtremely frequent, sub-millisecond, highly optimized.
Gen 1Buffer GenerationSurvivors of Gen 0 that outlive the initial collectionInfrequent; serves as a transition buffer.
Gen 2Long-LivedApplication lifecycles, static caches, singleton servicesRare; full collections sweep all generations (most expensive).
LOH (Large Object Heap)Large Blocks (≥ 85,000 bytes)Huge arrays, memory streams, large bitmapsCollected alongside Gen 2; not compacted by default to prevent expensive memory copying.

3. Finalizers (Destructors) & The Finalizer Thread

A finalizer (written as ~ClassName()) provides a safety net for cleaning up unmanaged OS handles if a developer forgets to call Dispose(). However, objects with finalizers survive Gen 0 collections and must wait for the dedicated CLR Finalizer Thread, causing memory retention.

4. The Standard IDisposable Implementation Pattern

For deterministic, immediate release of unmanaged resources (database connections, file handles, network sockets), implement IDisposable:

Standard Production IDisposable Pattern 
public class FileResourceManager : IDisposable
{
    private FileStream? _fileStream;
    private bool _disposed = false;

    public FileResourceManager(string filePath)
    {
        _fileStream = new FileStream(filePath, FileMode.OpenOrCreate);
    }

    // Public deterministic cleanup method called by consumers
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this); // Tells GC not to run finalizer!
    }

    // Protected virtual method for derived classes
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // Free managed objects (other IDisposable instances)
            _fileStream?.Dispose();
            _fileStream = null;
        }

        // Free unmanaged resources here if any exist
        _disposed = true;
    }

    // Finalizer safety net (only if unmanaged resources are directly owned)
    ~FileResourceManager()
    {
        Dispose(false);
    }
}

5. The using Statement & using Declaration

The using keyword guarantees that Dispose() is called even if an unhandled exception occurs inside the block:

Modern using Declaration 
// 1. Classical using statement (braced scope)
using (var stream = new FileStream("log.txt", FileMode.Open))
{
    // Stream is active
} // stream.Dispose() called here automatically!

// 2. Modern C# 8+ using declaration (scope ends at enclosing method exit)
void WriteAudit()
{
    using var writer = new StreamWriter("audit.txt");
    writer.WriteLine("Transaction executed.");
    // writer.Dispose() automatically invoked when WriteAudit() returns!
}

6. Memory Leaks in Managed Code & Traps

🟠 Compiler Trap & Common Gotcha

The #1 Memory Leak in .NET: Subscribing a short-lived object to an event on a long-lived or static object: 

GlobalPublisher.OnAlert += this.HandleAlert;

Why it leaks: GlobalPublisher holds an internal delegate pointer referencing this. As long as the publisher is alive, the GC considers this reachable from a GC root, preventing it from ever being collected!

Fix: Always unsubscribe when disposing: GlobalPublisher.OnAlert -= this.HandleAlert;.
